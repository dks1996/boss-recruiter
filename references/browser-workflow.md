# BOSS直聘浏览器自动化操作 SOP

本文件定义在 BOSS直聘上执行候选人搜索与沟通的标准操作流程和风控规范。Step 2 与 Step 4 执行前必须完整阅读本文件。

> **重要：本文件第一节的「有界面模式优先」是 2026-11 实战验证的关键结论，务必先读。** 用错浏览器模式会直接触发 BOSS 风控，整个流程走不通。

## 一、浏览器模式选择（关键，实战验证）

**结论：操作 BOSS 必须使用有界面模式（headless=false），不要用无头模式。**

这是 2026-11-18 在实际环境中反复验证得出的结论：

| 模式 | BOSS 表现 | 结论 |
|------|-----------|------|
| 无头模式（headless=true） | 打开首页立刻弹「安全验证：当前 IP 地址可能存在异常访问行为」，点一键验证后**升级为九宫格图片点选验证码** | ❌ 走不通，按红线必须停止 |
| 有界面模式（headless=false） | 正常打开企业后台页面，显示登录二维码，可正常扫码登录 | ✅ 可用 |

**根因**（避免误判）：当时查得出出口 IP 是家用宽带（联通），并非机房/数据中心 IP。所以「IP 被标记为数据中心」不是根因。真正原因是 **BOSS 能识别无头浏览器指纹**——这类环境一进来就触发验证。因此「换 IP / 重启光猫」通常无效，不要在这上面浪费时间。

**决策流程（每次启动前判断）：**

1. 用户能否看到浏览器窗口？
   - **能**（本地桌面、或可远程看到屏幕的环境）→ 用有界面模式（headless=false），用户真人扫码登录，继续自动化。
   - **不能**（远程云桌面、无显示环境）→ 有界面模式用户看不到、无法扫码/过验证码；无头模式又必被拦截。此时**不要强行自动化**，改为交付手动作战包（`财税顾问招聘作战包.md` 的生成逻辑），由用户手动操作。
2. 无论哪种情况：**遇到验证码/风控，按第五节红线立即停止，不识别、不破解**（详见第五节「验证码的正确处理原则」）。

## 二、能力检测与启用

1. 执行任何网页操作前，确认浏览器控制能力可用。当前环境使用的是 `browser-agent` skill（基于 Playwright，可直接调用系统 Edge，无需下载 Chromium 二进制）。
2. 能力不可用时的处理顺序：
   - 提示用户检查/启用浏览器控制能力；
   - 或通过插件市场安装 Browser Use / browser-agent 相关 skill；
   - 在能力恢复前，不得声称已完成搜索或沟通，不得编造候选人数据。
3. 浏览器控制只用于 BOSS直聘相关页面，不做无关浏览。

### 2.1 browser-agent 引擎调用速查（本机实测）

- Python：`C:/Users/Administrator/.workbuddy/binaries/python/versions/3.13.12/python.exe`
- 引擎脚本：`C:/Users/Administrator/.workbuddy/skills/browser-agent/scripts/browser_agent.py`
- 启动常驻服务：`python <引擎脚本> serve --port 8753 --browser edge --headless false`
  - 注意：服务启动参数里的 headless 只是默认值；每次 `launch` 时传的 `headless` 参数会覆盖它，务必在 launch 时明确传 `false`。
- 常用调用（`python <引擎脚本> call <方法> '<JSON参数>'`）：
  - `launch`：`{"browser":"edge","headless":false}`
  - `goto`：`{"url":"...","wait":"domcontentloaded"}`
  - `snapshot`：抓可交互元素（导航中可能返回 `about:blank`，此时改用 `eval` 判断真实状态）
  - `eval`：参数名是 `js`（不是 `expression`），可用于读 `location.href`、`document.body.innerText`
  - `click`：`{"selector":"[aria-label=\"...\"]"}`
  - `screenshot`：`{"path":"..."}`
  - `save_state`：`{"path":"..."}` 导出登录态
  - `close`：关闭会话
- 踩坑记录：
  - 页面跳转期间 `eval` 可能报 `Execution context was destroyed`——等 2-4 秒重试即可。
  - `snapshot` 偶发抓到空白页（`about:blank`），用 `eval` 读 `location.href` 才是真实 URL。

## 三、登录流程

1. 打开 BOSS直聘企业招聘端：`https://www.zhipin.com/web/chat/index`。
2. 检查登录状态。若显示「当前登录状态已失效」或跳到登录页，执行扫码登录：
   - 登录弹窗默认是「验证码登录/注册」，点左上角「APP扫码登录」切换到扫码模式；
   - 页面会跳转到独立的扫码登录页并显示二维码；
   - **把二维码截图发给用户**（用 `present_files` 展示），请其用手机 BOSS直聘 App 扫码，并**务必选择企业招聘账号**（非个人求职账号）；
   - 二维码有时效，过期就刷新页面重新截图；
   - 等用户确认扫码后，用 `eval` 检查是否已跳回企业后台。
3. 不要索取、记录或存储用户的账号密码、短信验证码。
4. 登录成功后确认进入企业后台（页面有「职位管理 / 推荐牛人 / 搜索 / 沟通」等菜单），而非个人求职端。若发现是求职端，提示用户切换账号再继续。

### 3.1 登录态复用（减少重复扫码）

- 登录成功后，用 `save_state` 把登录态（cookie + localStorage）导出到**工作区**文件（如 `boss-recruiter-data/storage_state.json`），下次 launch 时通过 `storage_state` 参数整体恢复，实现免重复扫码。
- **隐私红线**：登录态文件等同于账号凭据，**只存工作区**，严禁放进 skill 目录、严禁打包进分发包、严禁提交到 GitHub。
- 登录态失效时按正常扫码流程重新登录，不保存用户密码。

## 四、候选人搜索流程

1. 进入「人才搜索」或「推荐牛人」页面。
2. 按「岗位匹配标准卡」逐项设置筛选条件：岗位关键词、城市、工作经验、学历、年龄、期望薪资、活跃状态。
3. 执行搜索，记录本次搜索条件与结果数量。
4. 从结果列表逐条采集候选人卡片字段：候选人标识（姓名或匿名昵称）、当前职位、当前公司、工作年限、学历、技能标签、期望薪资、最近活跃时间、求职意向。
5. 对总分潜力较高的候选人，点击进入在线简历详情页，补充采集：工作经历要点、项目经验、教育背景、期望岗位、到岗时间。
6. 采集过程中遵守频率限制，不要快速连续翻页或高频点击。
7. 将采集结果写入结构化候选人列表，字段与 `scripts/build_shortlist.py` 的 `CANDIDATE_SCHEMA` 保持一致。
8. 采集后立即按 SKILL.md Step 2 的「历史去重」要求比对台账，跳过已沟通者。

## 五、沟通与索要简历流程

1. 只为 A、B 级候选人发送打招呼消息。
2. 发送前按 `references/message-templates.md` 生成个性化消息，逐条检查：是否引用了候选人真实经历、是否符合公司事实、是否包含清晰的公司卖点。
3. 通过浏览器控制发送消息，记录发送时间与候选人标识。
4. 每次操作后等待页面加载完成再读取结果，不要抢在渲染前操作。
5. 对已回复的候选人：
   - 先用追问语核实关键门槛；
   - 再索要完整简历或确认使用在线简历；
   - 更新沟通状态（已打招呼 / 已回复 / 已收简历 / 待跟进 / 拒绝 / 无响应）。
6. 收到简历后按 `references/screening-framework.md` 评估，回填评分与结论。
7. 沟通内容必须真实，不得代替用户做超出授权的承诺。

## 六、风控红线（必须遵守）

- 主动打招呼每小时不超过 20 人、每天不超过 100 人；两次操作之间加入 3-8 秒随机间隔，模拟真人节奏。
- 禁止给同一候选人短时间重复发送相同消息；禁止批量群发完全雷同的模板。
- 禁止绕过验证码、破解反爬、使用外挂或第三方群发工具。
- 禁止使用虚假身份、虚构公司信息或夸大承诺。
- 遇到以下任一情况，**立即停止全部自动化操作**并通知用户：
  - 页面出现验证码、安全验证、异常登录提示；
  - 平台弹出风控警告或限制操作提示；
  - 账号被要求重新登录或出现异常；
  - 候选人明确表示拒绝或投诉。
- 候选人隐私数据仅用于本次招聘，不对外传播，不在回复中展示无关个人信息。

### 6.1 验证码的正确处理原则（实战补充）

- **不识别、不破解**：无论图形点选、滑块还是短信验证码，都不用程序去识别或代点。即使用户口头告知选哪几格，让程序代点本质上仍是自动化破解，这条红线不越。
- **验证码是信号，不是障碍**：它是「当前浏览器环境不被信任」的信号。正确做法不是想办法过它，而是：
  1. 若在无头模式触发 → 停止，切换到有界面模式，让用户真人扫码/验证；
  2. 若在有界面模式仍触发 → 说明操作频率或行为异常，暂停并降低节奏，必要时改手动操作；
  3. 若用户环境看不到浏览器窗口 → 不强行自动化，交付手动作战包。
- 平台自带的「一键验证」按钮可以点（属于正常用户交互）；但点完若升级为图片/滑块验证码，立即停止。

## 七、异常处理

| 异常 | 处理方式 |
|------|----------|
| 无头模式触发安全验证/图片验证码 | 按第六节红线停止；改用有界面模式（headless=false），由用户真人扫码/验证 |
| 用户环境看不到有界面窗口（远程云桌面） | 不强行自动化，改用手动方案（作战包 + Excel 台账） |
| 扫码二维码过期 | 刷新登录页重新截图二维码 |
| 页面加载失败 | 等待后重试一次；仍失败则记录并跳过该候选人 |
| 页面跳转中 eval 报 context destroyed / snapshot 空白 | 等 2-4 秒重试，用 eval 读 location.href 判断真实状态 |
| 候选人信息缺失 | 标注「信息不足」，不强行编造，按低置信度处理 |
| 收到简历但无法解析 | 把原始内容记录到备注，提示用户人工查看 |
| 浏览器控制中断 | 保存已采集数据，通知用户从断点继续 |
| 用户要求停止 | 立即停止，保存已采集数据并输出阶段性结果 |

## 八、数据记录规范

- 每位候选人必须保留唯一标识，便于跨环节追踪。
- 每次沟通都要记录时间、内容与状态变化。
- 采集与评估过程中不臆造字段；信息不足时明确标注「信息不足」。
- 登录态文件、沟通历史台账含敏感信息，一律存工作区，不进 skill 包、不上 GitHub。
